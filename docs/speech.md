# Тезисы выступления: AccessEvent

## [0:00–0:30] Проблема и цель

Добрый день! Я защищаю проект AccessEvent — веб-платформу для организации
мероприятий, доступную людям с нарушениями слуха.

Проблема: обычные платформы мероприятий используют звуковые уведомления
и голосовой контакт, что делает их бесполезными для этой аудитории.

Цель проекта — платформа, где все ключевые события передаются визуально:
цветные уведомления, текстовая индикация статусов, фильтр по инклюзивным
мероприятиям.

## [0:30–1:30] Требования и стейкхолдеры

В ходе анализа я собрал 15 функциональных и 8 нефункциональных требований.
Ключевое нефункциональное — соответствие WCAG 2.1 AA: это стандарт
доступности интерфейсов.

Главный стейкхолдер — участник с нарушением слуха, его потребности
отражены в User Stories: визуальные уведомления, цветовая индикация
статуса регистрации, фильтр инклюзивных мероприятий.

Все требования и User Stories — в файле `docs/requirements.md`.

## [1:30–3:00] Архитектура и БД

Система построена по трёхслойной архитектуре:
- клиентский слой — HTML, CSS, JavaScript и шаблоны Jinja2;
- серверный — Flask с бизнес-логикой и JWT-авторизацией;
- слой данных — PostgreSQL (в тестах — SQLite).

База состоит из 3 таблиц: `users`, `events`, `registrations`. Связи видны
на ER-диаграмме. Роли `guest`, `user`, `organizer`, `admin` наследуют
права друг друга.

Подсистема безопасности: пароли хешируются, JWT-токен выдаётся при входе,
запросы к базе защищены от SQL-инъекций через ORM.

Подробности — в `docs/security.md`.

## [3:00–5:00] Демонстрация (переключиться на браузер)

Покажу сквозной сценарий:
1. Регистрирую организатора.
2. Создаю мероприятие и отмечаю его как инклюзивное — в списке появляется
   зелёный бейдж.
3. Регистрирую участника с отметкой «слабослышащий».
4. Записываю участника на мероприятие — статус виден жёлтым бейджем
   `pending`.
5. Показываю фильтр «Только инклюзивные» — остаются только доступные
   мероприятия.
6. Демонстрирую визуальное уведомление (красный баннер при ошибке) — без
   звукового сигнала.

Демонстрация подтверждает ключевые требования: FR-03, FR-06, FR-07,
FR-09.

## [5:00–6:00] Тестирование и качество

Автоматизированные тесты: 14 тестов pytest покрывают модели базы данных
и API-эндпоинты — регистрацию, вход, дубликаты, валидацию.

Все тесты проходят. В ходе ручного тестирования найдено 3 дефекта: два
исправлены, один зафиксирован в `bug_reports.md` с обоснованием.

Все пять проверок GitHub Actions зелёные — это подтверждает целостность
проекта.

## [6:00–7:00] Оценка и развитие

По SWOT-анализу:
- сильные стороны — полная инклюзивность и автоматизация через CI/CD;
- слабые — нет push-уведомлений и мобильного приложения.

Направления развития: push-уведомления, перевод видео в субтитры через ИИ,
интеграция с календарями.

Проект готов к сопровождению: есть административная документация и
контейнеризация.
